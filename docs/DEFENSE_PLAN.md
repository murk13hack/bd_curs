## Блок 2. Общая архитектура (4–5 мин)

*Глава 4 записки, рис. 14 — развёртывание.*

### 2.1. Схема компонентов

```
Браузер → nginx (frontend :80) → FastAPI (backend :8000) → PostgreSQL 16 (db)
                ↑ proxy /api/              ↑ APScheduler → CALL sp_*
```

**Три контейнера Docker Compose:** `ptt-frontend`, `ptt-backend`, `ptt-db`. Сеть `ptt-net`, том `pgdata` для данных PostgreSQL.

### 2.2. Принцип «тонкий backend, тяжёлая БД»

| Слой | Ответственность |
|------|----------------|
| **PostgreSQL** | CHECK, FK, триггеры, `fn_*`, `sp_*`, VIEW, MATERIALIZED VIEW, FTS, планировщик через процедуры |
| **Backend** | HTTP, Pydantic-валидация, ORM для простого CRUD, `CALL`/`SELECT` для сложного |
| **Frontend** | UX, формы, графики; **не** считает streak, не решает overdue |

### 2.3. Поток одного действия (завершение задачи)

Проговорить цепочку из § 4.2 записки:

1. Кнопка «Выполнено» в UI → `POST /api/v1/tasks/{id}/complete`
2. FastAPI → `CALL sp_complete_task(id)`
3. PostgreSQL: UPDATE + триггеры (`completed_at`, возможно `overdue`, audit, recurring)
4. JSON-ответ → обновление экрана

**Фраза для комиссии:** «Если завтра заменить React на мобильное приложение, правила просрочки и аудита останутся в БД без переписывания логики.»

### 3.3. Примеры целостности (2 мин)

Из **каталога целостности** (глава 11):

- `tasks_deadline_after_created`, `tasks_start_before_deadline`
- `diary_entries` — одна запись на `(user_id, entry_date)`
- `trg_tag_user_match` — тег того же пользователя, что задача/дневник
- Ошибки → HTTP 409/400 через `IntegrityError` на backend (но **источник правила — БД**)

### 3.4. Логика в СУБД — три класса объектов (4–5 мин)

#### Функции `fn_*` (возвращают результат, вызываются SELECT)

| Функция | Зачем на защите |
|---------|-----------------|
| `fn_get_calendar_stats` | Агрегат месяца: задачи, дневник, праздники, цвет дня |
| `fn_search_diary` | FTS `russian` + `ts_rank` + сниппет |
| `fn_calculate_streak` / `fn_calculate_anti_streak` | Серии паттернов |
| `fn_goal_progress` | Прогресс цели |
| `fn_next_recurring_date` | daily/weekly/monthly/custom |

#### Процедуры `sp_*` (CALL, транзакции, фон)

| Процедура | Кто вызывает |
|-----------|--------------|
| `sp_complete_task` / `sp_reopen_task` | API задач |
| `sp_log_pattern_response` | API паттернов |
| `sp_spawn_recurring_tasks` | APScheduler 00:05 |
| `sp_ensure_habit_logs_for_day` | scheduler + API «сегодня» |
| `sp_recalc_calendar_cache` | каждые 10 мин → REFRESH `v_overdue_tasks` |
| `sp_export_user_data` / `sp_import_user_data` | backup |

#### Триггеры (обязательная автоматика)

- `trg_task_overdue_check` — done после deadline → **overdue**
- `trg_diary_tsv_update` — синхронизация FTS-вектора
- `trg_audit_*` — журнал изменений в `audit_log`
- `trg_recurring_spawn_on_complete` — следующий экземпляр повторяющейся задачи

### 3.5. Представления и OLAP (2–3 мин)

- Обычные VIEW: `v_task_topic_breakdown`, `v_pattern_streaks`, `v_weekly_summary`, …
- **Материализованное** `v_overdue_tasks` — кэш просрочки, обновление процедурой (компромисс скорость/актуальность).
- **OLAP:** `v_olap_daily_facts` — зерно «день × пользователь»; срезы на API `/stats/olap` (рис. 9 в записке).

### 3.6. Нормализация (1 мин)

- Схема в **3НФ**: нет транзитивных зависимостей в неключевых полях.
- Допустимая денормализация: `content_tsv` в дневнике (поддерживается триггером), MATERIALIZED VIEW для просрочки.

### 3.7. Live-SQL (если спросят или есть 2 мин запаса)

В `psql`:

```sql
-- Просроченные из кэша
SELECT id, title, deadline FROM v_overdue_tasks LIMIT 5;

-- Календарь на текущий месяц (фрагмент)
SELECT * FROM fn_get_calendar_stats(1, 2026, 5) LIMIT 7;

-- FTS
SELECT * FROM fn_search_diary(1, 'продуктивность', 3);
```

- Сослаться на **главу 10**: EXPLAIN ANALYZE, рис. 11–13 (индексы GIN, partial, BRIN).

## Блок 4. Backend (8–10 мин)

*Глава 6 (аспект API), код в `backend/app/`.*

### 4.1. Стек и структура

- **Python 3.12, FastAPI, SQLAlchemy 2 async, asyncpg**
- Точка входа: `backend/app/main.py` — lifespan запускает **APScheduler**
- Роутеры: `backend/app/api/v1/` — tasks, diary, patterns, calendar, stats, goals, import_export, …
- Префикс API: `/api/v1` (через nginx с фронта — `/api/v1/...`)

### 4.2. Подключение к БД

- `DATABASE_URL` = `postgresql+asyncpg://...@db:5432/ptt`
- `get_session()` — одна AsyncSession на HTTP-запрос
- `default_user_id = 1` — одно-пользовательский режим (`deps.py`)

### 4.3. Три способа работы с БД (проговорить с примерами)

| Способ | Когда | Пример |
|--------|-------|--------|
| ORM | CRUD | `POST /tasks` → `session.add(Task)` |
| SELECT к fn/VIEW | Аналитика | `GET /calendar/2026/5` → `fn_get_calendar_stats` |
| CALL sp_* | Атомарные операции | `POST /tasks/{id}/complete` → `sp_complete_task` |

**Акцент:** завершение задачи — **не** `UPDATE` из ORM, а процедура (см. `tasks.py`).

### 4.4. Планировщик

`scheduler.py` — фоновые `CALL` без участия пользователя:

- 00:05 — повторяющиеся задачи
- 00:10 — логи привычек на день
- каждый час — закрытие пропущенных откликов паттернов
- каждые 10 мин — refresh материализованного представления
- вс 03:00 — архивация audit

### 4.5. Обработка ошибок

- `IntegrityError` → `db_errors.py` → HTTP 400/409 с текстом на русском (имя constraint в PostgreSQL).

### 4.6. Демо backend (3–4 мин)

1. Открыть **http://localhost/docs** (Swagger через nginx).
2. `GET /api/v1/ping` или `/health` — живость.
3. `GET /api/v1/tasks?limit=5` — список из ORM.
4. `POST /api/v1/tasks/{id}/complete` — показать, что статус меняется через процедуру (в UI или повторный GET).
5. `GET /api/v1/calendar/{year}/{month}` — ответ из функции БД.
6. (Опционально) `GET /api/v1/stats/olap?...` — OLAP-срез.

### 4.7. Тестирование (30 сек)

- Упомянуть pytest в `backend/tests/` — CRUD, diary FTS, API контракты.

### 6.1. Docker Compose

Проговорить `docker-compose.yml`:

| Сервис | Образ / сборка | Порты | Зависимости |
|--------|----------------|-------|-------------|
| `db` | postgres:16-alpine | внутренний 5432 | volume `pgdata`, mount `./db/init` |
| `backend` | build `./backend` | 8000 | `depends_on: db healthy` |
| `frontend` | build `./frontend` | 80 | `depends_on: backend healthy` |

Healthcheck на всех трёх — оркестрация «db → backend → frontend».

### 6.2. Конфигурация

- `.env` из `.env.example`: `POSTGRES_PASSWORD`, `TZ`, `VITE_API_URL=/api/v1`
- Команда запуска: `docker compose up -d --build`

### 6.3. nginx как единая точка входа

- Статика React: `location /` → `try_files` → `index.html` (SPA).
- `location /api/` → proxy на `backend:8000`
- Прокси `/docs`, `/health` — удобство для защиты без запоминания порта 8000.

### 6.4. Жизненный цикл данных

| Ситуация | Действие |
|----------|----------|
| Первый запуск | init `db/init` автоматически |
| Обновление кода на старом volume | `db/migrations/00N_*.sql` вручную |
| Полный сброс | `docker compose down -v` (удалит pgdata!) |

### 6.5. Демо деплоя (1–2 мин)

```powershell
docker compose ps
docker compose logs backend --tail 20
```

Показать в логах backend строки `APScheduler started`, `sp_recalc_calendar_cache executed` — связь runtime с БД.

## Блок 8. Возможные вопросы комиссии

| Вопрос | Краткий ответ |
|--------|--------------|
| Почему PostgreSQL, а не MySQL/SQLite? | JSONB, MATERIALIZED VIEW, PROCEDURE, FTS `russian`, EXCLUDE/gist, расширения — требования ТЗ по СУБД |
| Где 3НФ нарушена? | `content_tsv` — денормализация под FTS, согласована триггером |
| Зачем процедура, если можно UPDATE из Java? | Одна транзакция, единые триггеры/audit, нельзя обойти правила другим клиентом |
| Чем VIEW отличается от MATERIALIZED VIEW? | Обычное — всегда актуально; материализованное — снимок, быстрее, refresh по расписанию |
| Как работает FTS? | Триггер пишет `to_tsvector('russian', content)`, GIN-индекс, `fn_search_diary` с `@@` и `ts_rank` |
| Что при падении backend? | Данные в `pgdata` сохраняются; scheduler не работает — повторения/логи habit до рестарта |
| Миграции vs init? | Init — только новый volume; существующая БД — SQL-файлы в `db/migrations/` |
| Streak считается в JS? | Нет — `fn_calculate_streak`, отображение через `v_pattern_streaks` |
| Сколько индексов и зачем partial? | См. глава 7 и 10; partial уменьшают размер под выборки «только с deadline» |
| OLAP — это отдельная БД? | Нет, VIEW `v_olap_daily_facts` + агрегация в API |
